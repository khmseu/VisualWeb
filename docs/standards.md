# Standards sources, support status, and local reference documents

The authoritative source registry is [specs/manifest.json](../specs/manifest.json).
It records IDs, official URLs, local filenames, fetch/check timestamps and HTTP
validators. The local HTML files live under `specs/cache/`; this generated
directory is ignored by git to avoid large document churn. The registry is
tracked. Each developer/agent checkout bootstraps its own local cache once.
Implemented subsets and explicit omissions are recorded in the support inventory
below.

From the repository root:

```sh
dotnet run --project tools/SpecCache -- specs/manifest.json
```

Missing/empty files are fetched even if metadata is fresh. Otherwise files last
checked **more than 30 days ago** are revalidated using ETag/Last-Modified when
available. A 304 advances `checkedAt`, not `fetchedAt`; successful downloads
advance both. Fresh files cause no HTTP requests. Refresh is explicit: builds
and tests never download or refresh documents. Agents should run the refresh
as part of standards-dependent work, not every tool call.

Keep cache documents for offline work. Failed downloads retain existing copies,
leave failed entries stale and return a nonzero exit code; report stale evidence
instead of silently claiming current standards. `--force` revalidates every
entry (it still uses conditional requests where possible).

## Interface citation convention

Use XML docs linking the official source and anchor, plus the registry ID:

```csharp
/// <summary>Parses a URL using the supported WHATWG algorithm subset.</summary>
/// <remarks>
/// Spec: url; <see href="https://url.spec.whatwg.org/#concept-basic-url-parser">basic URL parser</see>.
/// </remarks>
```

Read the corresponding section in `specs/cache/url.html` first. OS/internal
interfaces need relevant SDL/.NET/OS API documentation when appropriate,
not invented web-standard citations. The tool keeps source HTML with its
copyright/license notices intact; cached standards remain subject to their
publishers' terms and are not project-authored documentation.

## Support status

This inventory records the current support status of web-platform standards
and related specifications used by VisualWeb. It is a scope guide, not a
conformance declaration or a substitute for the subsystem documentation and
tests. A standards citation, cached source, or passing fixture family does not
by itself establish conformance.

### Approximate coverage estimates

The percentages are coarse engineering estimates of how much of each standard's
applicable feature surface appears implemented, inferred from the scope
described by each row and its linked guides. They use 5% increments and are not
calculated from normative clauses, test counts, or a formal coverage model.
Estimates across different standards, or rows that group multiple standards,
are not rigorous apples-to-apples measurements; the
[Missing priority](../plans/Missing.md#recommended-priority) uses them only as
a rough selection heuristic. They are not conformance scores; the scope
descriptions and subsystem guides remain the authoritative account of behavior
and omissions.

- **~0%** means no implementation of the described standard features.
- **~5%–~95%** means a documented subset is implemented.
- **100%** is reserved for a standard whose complete applicable requirements
  have been demonstrated. VisualWeb currently makes no full-conformance claim
  for any web standard in this inventory.

The scope is the web standards and Unicode/RFC sources in the
[standards registry](../specs/manifest.json) that define implemented or
planned web-facing behavior. SDL, .NET, OS, HarfBuzz, Skia and ClearScript
documents are implementation/API references, not web-platform conformance
claims, and are not listed as supported standards here.

### Implemented subsets

Script-facing `Element.innerHTML` now uses context-sensitive
[HTML fragment parsing](../specs/cache/html.html#parsing-html-fragments) and
the [HTML fragment serialization algorithm](../specs/cache/html.html#html-fragment-serialisation-algorithm),
with getter/setter behavior from
[HTML `innerHTML`](../specs/cache/html.html#the-innerhtml-property). A checked
native replacement follows [DOM replace all](../specs/cache/dom.html#concept-node-replace-all).
The implementation is limited to the supported HTML-only parser contexts,
bounded by explicit budgets, does not sanitize output, and does not execute or
schedule inserted scripts or load resources. SVG, MathML, frame/frameset,
unsupported table/select algorithms, namespaces and shadow roots remain out of
scope. The HTML (~20%) and DOM (~20%) estimates are unchanged.

For an in-body table start, HTML tree construction closes an in-scope
paragraph only when the document is not in quirks mode; quirks mode preserves
the paragraph around the table. The overall HTML estimate remains unchanged.

The [in-body](../specs/cache/html.html#parsing-main-inbody) ignored
table-structure start-tag rule also applies inside selects and select-context
fragments. Unmatched table-structure end tags in that in-body select context
use generic end-tag recovery; in-cell rules remain separate.
In initial, before-html, before-head, in-head and after-head modes, structure
start and end tags follow the existing document-mode reprocessing and
unexpected-end-tag rules.
In scripting-disabled head-noscript mode, table starts close `noscript` and
are reprocessed, whereas table end tags are ignored with a parse error.
Table and table-structure tokens in after-body and after-after-body modes
report a parse error and are reprocessed in-body; after-body also applies to
HTML fragments.
In frameset, after-frameset and after-after-frameset modes, those tokens
report a parse error and are ignored.
The same frameset-mode recovery ignores `svg` and `math` starts; actual
foreign-content tree construction remains unsupported.
Column-group fragments also diagnose and ignore those starts when the current
node is not a `colgroup`; foreign starts in an open document `colgroup` remain
unsupported.
The overall HTML estimate remains unchanged.

For an in-body `select` start, the select fragment context ignores the token;
otherwise an in-scope select is closed and the token ignored, while a select
beyond a scope boundary does not prevent insertion. Table-mode starts continue
to use foster parenting. Other select algorithms remain bounded.
For an in-body `input` start, the select fragment context ignores the token;
otherwise an in-scope select is closed before inserting the input, while an
out-of-scope select remains open. In-table hidden inputs retain their separate
insertion rule.
Generic in-body end-tag recovery (including option and optgroup ends)
stops at special elements and generates implied ends except the matching name
before the misnesting check, including in fragments.
Select ends instead require a select in scope, generate implied ends and close
it, diagnosing any remaining descendants; non-boundary special elements do not
block this scope-based rule.
In-body non-heading block and button ends similarly generate implied ends
before checking remaining descendants when the target is in scope. Fostered
and fragment paths share this behavior. Heading ends require any heading in
scope, generate implied ends and close the nearest heading, with a diagnostic
for a mismatched name or remaining descendant.
In-body `li`, `dd` and `dt` ends require their respective scope and generate
implied ends except for the target before diagnosing remaining descendants.
In-body `option` starts generate implied end tags except `optgroup` when select
is in scope, diagnose an option still in scope, and reconstruct formatting.
Without an in-scope select, only a current option is closed before insertion.
In-body `optgroup` starts generate all implied end tags with a select in scope,
diagnose a remaining in-scope option or group, and reconstruct formatting.
Without an in-scope select, they close only a current option.
In-body `hr` starts close an in-button-scope paragraph using implied end tags,
then generate implied ends and diagnose remaining in-scope options or groups
only when a select is in scope. Fragment and fostered paths use the same rule.

Document `noscript` uses the
[parser scripting state](../specs/cache/html.html#parser-scripting-disabled).
Disabled scripting selects the dedicated
[in-head-noscript mode](../specs/cache/html.html#parsing-main-inheadnoscript)
in the head and ordinary
[in-body handling](../specs/cache/html.html#parsing-main-inbody) in the body;
enabled scripting selects RAWTEXT through the
[in-head](../specs/cache/html.html#parsing-main-inhead) and in-body rules. This
does not add full script preparation. `noscript` fragment contexts use the
fragment algorithm's scripting-disabled Data state; the API does not expose
scripting-enabled fragment parsing. See the
[HTML fragment parsing algorithm](../specs/cache/html.html#parsing-html-fragments).
The overall HTML estimate remains unchanged.

HTML tree construction includes token-snapshot active formatting, the
order-independent three-entry Noah's Ark rule, reconstruction and
template/caption/cell markers, plus the no-furthest-block and bounded
furthest-block adoption-agency branches. Nested table starts inside captions use
the bounded in-body table rules and restore caption mode on close, including
template contents and caption fragments. Furthest-block recovery includes
inner-loop clone/removal, bookmark/index shifts, reparenting and open-stack/list
replacement. The outer loop is capped at eight iterations, inner-list removal
follows the after-three-iterations rule, generated nodes count toward parser
limits, and adjusted fragment/template insertion parents are honored.
Non-whitespace table text uses the last open template's contents as the foster
location when it follows all open tables, including when no table is open.
Nested anchor and `nobr` starts use bounded adoption recovery, with original-anchor
removal and `nobr` post-adoption reconstruction respectively. Non-hidden input
starts in table, table-body and row modes use in-body handling with bounded
foster-parent insertion; inputs in cells use ordinary in-body insertion.
Body/head starts and unmatched head ends in table, table-body and row modes use
the corresponding fostered in-body recovery; body attributes merge into the
existing body, and head tags are not inserted.
`br` and `hr` starts and end tags in those table modes also follow in-body
handling with bounded foster-parent insertion. `</br>` is handled as a `br`
start tag; an unmatched `</hr>` is ignored by in-body recovery. Block-element
starts and end tags in those modes also follow in-body handling with bounded
foster-parent insertion. This covers the `image` alias, `img` and `wbr` start
and end tokens, `div`, `p`,
`pre`, `listing`, `h1`-`h6`, `li`, `dd`, `dt`, `button`,
`address`, `article`, `aside`, `blockquote`, `center`, `details`, `dialog`,
`dir`, `dl`,
`fieldset`, `figcaption`, `figure`, `footer`, `header`, `hgroup`, `main`,
`menu`, `nav`, `ol`, `search`, `section`, `summary` and `ul`. Other supported
void-element tokens (`area`, `base`, `basefont`, `bgsound`, `embed`, `keygen`,
`link`, `meta`, `param`, `source` and `track`) use the same bounded route;
resource loading is not implied. `textarea` starts and unmatched end tags use
the same route; starts enter RCDATA with initial-line-feed suppression, and the
matching end tag restores the original table insertion mode. `title` starts
and unmatched end tags use the same route, entering RCDATA without initial-LF
suppression. `iframe`, `noembed` and `noframes` starts and unmatched end tags
also use that route with RAWTEXT tokenization; no browsing context or resource
loading is added. `xmp` starts and unmatched end tags also use the route,
retaining its in-body paragraph/formatting handling before RAWTEXT. `pre` and
`listing` retain initial-line-feed suppression. Template starts and matching
ends in table, table-body and row modes use in-head/template processing and
restore the originating table insertion mode on close. Template contents select
bounded table modes for supported caption/column/section, row and cell starts.
A `select` start within template content uses the bounded in-body/select parser;
templates started while processing a select use bounded in-body/template
processing, do not route their contents through the enclosing select's token
rules, and resume the enclosing select's token handling on close, including
for select-context fragments. The fragment-context `select` start rule still
applies inside template content.
Other unsupported table/template algorithms remain
unsupported. Form starts inside template contents, including template-context
fragments, ignore and preserve the outer form pointer; in-body form ends close
an in-scope form, while in-table starts insert and pop without changing the
pointer. The script-facing form property and other scripting remain deferred;
the bounded native DOM query is documented below.
Outside template contents, a form end clears the form pointer before its scope
check, including when a table or fragment puts the pointed-to form out of scope.
An in-scope form end generates implied end tags and removes the pointed-to form
from the open stack, leaving misnested descendants open with a diagnostic.
Other in-body end-tag closures may pop the pointed-to form from the open stack
while leaving the form pointer set; later form starts remain ignored until a
form end clears it. Adoption's form-removal guards are unreachable in the
current HTML-only stack because `form` is special and becomes the furthest
block rather than a removed intermediate node; the guards remain in place.
Formatting-element start/end tags, including `a`, and `span`
start/end tags use bounded in-body foster parenting in table, column-group,
table-body and row modes, including existing bounded nested-anchor and
nested-`nobr` recovery. `option`, `optgroup` and `label` starts and ends use the
same path; column-group fallback closes the open `colgroup` before table-mode
reprocessing, and unmatched `label` ends receive in-body recovery. Bounded
adoption selects the first special element below the formatting element and
uses the foster insertion location for reparenting when needed.
`abbr`, `cite`, `data`, `dfn`, `kbd`, `mark`, `q`, `samp`, `sub`, `sup`,
`time` and `var` start and end tags also use bounded fostered in-body handling
in these modes; other non-special names, including unknown and custom element
names, use the same path. Unmatched ends retain in-body recovery; no
custom-element reactions are implemented.
`applet`, `marquee` and `object` start/end tags use bounded in-body
active-formatting-marker handling, including fostered processing in table,
table-body and row modes. This creates static DOM elements only; plugin,
external-resource behavior remain unsupported. Fragment parsing with these
contexts uses the same bounded in-body handling.
Other end tags not covered by table-specific rules use the generic fostered
in-body fallback in table, table-body and row modes; unsupported table starts
remain explicit failures.
`select` starts and unmatched end tags in those modes also use bounded fostered
in-body handling; an open select uses the existing bounded select-token rules.
`ruby`, `rb`, `rtc`, `rp` and `rt` start/end tags use the same path, retaining
the existing bounded ruby annotation recovery.
`plaintext`
starts and unmatched end tags use in-body foster parenting in those modes; a
start switches to PLAINTEXT and consumes the remainder of the input as literal
text. Character tokens are buffered as table text only when the current node is
`table`, `tbody`, `template`, `tfoot`, `thead` or `tr`; otherwise they use
in-body handling, preserving text inside a fostered element. Non-whitespace
table-character runs (including
adjacent whitespace) are foster-parented before the nearest table when the
current node is table-related; whitespace-only runs stay in the table.
Non-whitespace runs reconstruct active formatting at the foster location when
needed. If a parser-script callback detaches the last open table, fostered
table text appends to the preceding open-stack element. When the table is
moved directly under a `Document`, fostered text is discarded under the
[insert a character algorithm](https://html.spec.whatwg.org/multipage/parsing.html#insert-a-character);
other parented tables retain insertion before the table. `frame` and
`frameset` starts in table modes also use the generic
fostered in-body fallback without adding frame browsing contexts, loading or
rendering. This increment does not change the coarse HTML percentage below.
Unimplemented table start tokens requiring foster parenting remain unsupported.
The unchanged ~20% HTML estimate also includes bounded document-mode frameset
tree construction (including frameset-ok gating and nested frame nodes); this
does not implement frame browsing contexts, resource loading or rendering.
The native DOM also provides a computed form-owner query for built-in listed
form-associated elements; parser-inserted association state, custom elements
and script-facing form APIs remain unsupported. The coarse HTML estimate remains
unchanged.
Ordinary in-body parsing and body-context fragments also report a parse error
and ignore `caption`, `col`, `colgroup`, `tbody`, `thead`, `tfoot`, `tr`, `td`
and `th` start tags instead of rejecting the document. This does not broaden
table-mode recovery or the selected tree-fixture families; the coarse HTML
estimate remains unchanged.

Opted-in parser-inserted inline classics ignore `async` and `defer` and run at
their parser position, per HTML
[script preparation](https://html.spec.whatwg.org/multipage/scripting.html#prepare-the-script-element)
(local ID `html`). External classic `async`/`defer` scheduling remains unsupported;
the coarse HTML estimate remains unchanged.

The opted-in loaded-page script facade also reflects
[`HTMLElement.hidden`](https://html.spec.whatwg.org/multipage/interaction.html#dom-hidden)
using the cached HTML getter/setter rules (local ID `html`). This does not add
the `hidden=until-found` reveal lifecycle or broaden the current layout subset.
An offline local/process browser regression composes the supported table
parser, script-driven DOM queries/`innerHTML`, and form-control snapshots; it
does not expand the HTML or DOM conformance estimates.

### CSS standards

selector, layout and paint subset. Unsupported syntax/features produce

support. See the [CSS](css.md), [Text and layout](text-layout.md), and
[Painting](painting.md) guides for exact details.

### Referenced but not implemented

| Standard or source ID                    | Current relationship                                                                                                                        |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| WHATWG MIME Sniffing (`mime-sniffing`)   | MIME type parsing/serialization exists, but context-dependent byte sniffing and MIME classification are deferred. See [Core](core.md#mime). |

The Public Suffix List (`public-suffix-list`) is pinned data used by the bounded
networking matcher and HSTS policy, not a web-platform standard whose full
behavior VisualWeb claims to implement. Likewise, passing WPT, html5lib, or
other focused tests is evidence for only the tested cases and documented
subset.

### Keeping this inventory current

When a change adds, removes, or materially changes standards-defined behavior:

1. Update the relevant status and scope row here in the same change.
2. Keep the owning subsystem guide and standards registry consistent; add a
   registry entry when a newly referenced source is introduced.
3. Use a coarse approximate coverage estimate unless the complete applicable
   standard has been verified; describe important omissions explicitly. Do not
   infer support from a citation, project name, API shape, or test count.

For source refresh and cache workflow, see the instructions at the start of
this document; for interface citation rules, see the
[Interface citation convention](#interface-citation-convention).
